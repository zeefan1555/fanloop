# Bounded RemNote Tasks And Impact-Based Maintenance

The user approved generic card/workflow optimization and a separate RemNote Direct
maintenance Workflow, then requested implementation through self-iteration.
General means independent of a particular article, KB ID, fixture, data size or
bug. It does not mean a universal batch engine or release platform.

Keep ADR-0117's four card steps, order and executors. Ordinary, original-import and
original-excerpt modes retain their content rules; independent goals still produce
0..N cards. Use existing bounded context/task/verification APIs and private recovery
journals. Plan limits do not authorize truncating content, changing modes or
ignoring unknown outcomes. Exact native IDs, review history, daily/HOME placement,
source integrity and full affected Wiki zero-card proof remain mandatory.

Complete fresh task evidence may satisfy a structural check without repeating
individual SDK calls. Any later affected mutation, stale/partial read, reconnect
or session change requires reconciliation. Hashes never replace final semantic
review. Ordinary card tasks do not upgrade tools or run release/replay stress
suites. Tool defects belong to a separate maintenance Requirement that preserves
the blocked card task's IDs and keys.

Add remnote-direct-maintainer as the fourth local complete bundle, amending only
ADR-0124's three-package inventory. Its four Agent steps are define_change,
build_candidate, verify_candidate and deliver_change. Every normal/rework route
retains ADR-0119 Panorama. The explicit package Workflow ID is a repository
maintenance entry; adding it does not rebuild the Fanloop CLI or silently alter
an installed static scenario selector.

Maintenance checks follow the union of actual documentation, CLI-read, CLI-write,
plugin/protocol and installation impact. Two-card smoke is not universal
acceptance. Repository instructions supply Git policy, commands and installation
bindings; runtime supplies exact authorized KB and capability facts. The accepted
candidate is frozen, tested, pushed, checked at the exact remote SHA and then
adopted locally when applicable. CLI-only business changes preserve plugin assets.
Every completed validated Direct change is committed/pushed; unrelated dirty work
and private data are excluded.

Use the existing architecture: CLI business composition over an authenticated
local WebSocket and SDK plugin. Do not add a server, arbitrary code executor,
compatibility layer, speculative platform adapter or marketplace release. A local
installation restore is not native KB rollback; unsupported capabilities and
unknown writes remain explicit failures/limitations.

This is configuration delivery under ADR-0125, with strict affected-package loading,
route matrices, a fresh independent behavior trial, Git delivery and loaded-source
readback. Executable Direct changes and native persistence acceptance are separate
candidates; configuration-only trials must not claim that runtime evidence.
Performance comparisons record mode/workload and separate planning, SDK/CLI work,
verification and environment wait; a sample card count or elapsed time is not a
product success condition.
