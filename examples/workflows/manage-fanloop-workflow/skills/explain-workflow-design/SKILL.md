# 把 Workflow 讲到一眼就懂

读取当前 Step 已形成的结构化数据，只负责解释和展示。不得改变 Workflow 设计、候选内容、验证结论或人工决定。

页面交付前必须通过“儿童复述检查”：一个从未听过 Fanloop 的人看完第一屏后，不使用专业术语，也能回答：

1. 用户想改什么。
2. 以前是什么样。
3. 现在准备怎么改。
4. 哪些东西不会变。
5. 现在需要人决定什么。

任一问题答不出来，就继续改页面，不得返回可视化完成 Condition。

## 先翻译，再排版

正式术语第一次出现前，先用常用词说清楚；术语只放在后面的括号里：

- Output：最后必须交出来的东西。
- Condition：能证明这件事真的完成的检查。
- Route：检查结果决定接下来往哪里走。
- Step：谁在什么时候做哪件事。
- Skill：Agent 必须照着做的说明。
- Human Gate：必须等人亲自决定的门。

第一屏标题使用具体动作，不使用“架构设计”“流程建模”“审核总览”等抽象词。每句话只表达一个事实或动作，
最多使用一个逗号。删掉“本页将展示”“点击查看详情”等页面自述。

## 第一屏固定任务

第一屏只完成一条连续主线，不摆一排等权卡片：

1. 原样保留用户要求，并压成一句不丢语义的人话。
2. 用本次真实对象画出“改前 -> 改后 -> 等待决定”。
3. 涉及 Condition-first 时，把真实 Route AND 组画成“要交的东西 -> 全部证明 -> 门打开”；缺一项时明确画回流。
4. 直接标出新增、删除、调整、不变。颜色只辅助，文字标签必须同时存在。
5. 第一屏底部露出下一节标题，让读者知道下面还有精确内容。

画面必须与本次候选直接相关。不得复用固定小火车、通用流水线、抽象卡片墙或与候选无关的故事。可以使用
自包含 HTML、CSS 或内联 SVG；不依赖外部脚本、字体、图片或网络请求，不内联 Base64。

## 信息分层

主页面按以下顺序：

1. 用户原始要求。
2. 一句话变化。
3. 真实改前和改后。
4. 会影响与不会影响。
5. 一个真实失败反例。
6. 未验证内容和风险。
7. 当前要人决定的问题。

Step、Condition/Route、Output、Skill 先用人话表述，再给正式名称。完整 YAML、Diff、Step 映射、候选摘要和
验证 argv/stdout/stderr 放进折叠技术区；不能删除，也不能挡住主线。

## 三个阶段

- 分析阶段：未生成的内容明确标为“计划”。第一屏解释为什么这样设计。
- 构建阶段：显示精确候选身份、真实文件变化和真实拓扑，不再使用“计划”冒充结果。
- 发布阶段：保留人工批准时的主线、候选内容和摘要，只追加发布状态、配置地址、版本 Diff、Doctor 结果和
  `fanloop update config` 用户动作。`fanloop update` 只切换 CLI Release，不会同步 Workflow 配置。

每个 Requirement 只维护同一份 L2 飞书文档中的一个主 HTML Block。每次写入后重新读取文档，确认 HTML Block
存在，记录真实 `block_id`、`revision_id` 和内容摘要。嵌入、权限或回读失败时保持 blocked，不用本地文件代替交付。

## 版面底线

- HTML 小于 500KB，适配约 820px 文档区和 375px 手机宽度。
- 不嵌套卡片，不使用装饰性渐变、光斑或单一色调。
- 固定格式元素使用稳定尺寸；文本不得溢出、遮挡或推动相邻结构跳动。
- 点击控件可触摸、可键盘操作，并有清楚名称。
- 正文不解释页面怎么用，不展示键盘快捷键。

## 失败反例

错误表达：`Output contract 和 Condition matrix 闭合后进入 next_step_id。`

正确表达：`先说最后要交什么。再拿出全部证明。证明齐了，门才打开。`
