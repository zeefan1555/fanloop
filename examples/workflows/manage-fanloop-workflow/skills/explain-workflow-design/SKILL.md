# 生成人一眼能审核的 Workflow 变更页

读取当前 Step 已形成的结构化数据，只负责解释与展示，不改变 Workflow 设计、候选内容或审核决定。

假设审核人从未听说过 Fanloop 或 Workflow。页面的任务不是介绍管理流程，而是让人快速回答：用户要求改什么，
候选准备怎么改，影响哪里，风险是什么，是否可以批准。先用常用词讲清楚真实变化，再出现 Step、Condition、
Route、Output 和 Skill 这些正式名称。必须给出一个与本次候选直接相关的失败反例。

制作一个单页、手机优先的 HTML 解释页：

1. 第一屏必须是本次变更的审核总览，不得用固定小火车、通用流程故事或一排文字卡片代替。使用自包含的
   HTML、CSS 或内联 SVG 直接展示“用户要求 -> 改前 -> 改后 -> 等待决定”。即使不读正文，也能猜出本次
   候选改变了什么。
2. 每句话只表达一件事，使用短句、常用词和具体动作，避免连续堆叠术语。
3. 多步骤内容提供简单的点击控件；控件必须可触摸、可键盘操作，并保持稳定尺寸。
4. 页面自包含，不依赖外部脚本、字体、图片或网络请求，不内联 Base64。
5. 默认页面按以下顺序展示：用户原始要求、目标与基线、一句话方案、真实改前/改后、影响与不变边界、风险与
   未验证内容、需要人决定的问题。完整 YAML、Diff、Step 映射和验证证据放在清楚标记的技术区。
6. 审核图必须突出新增、删除、改名、重排、executor 变化、Human Gate 和未验证边界。
7. 交付图必须同时给出目标 Workflow 配置地址、版本 Diff 地址、发布结果和 `fanloop update config` 用户动作。`fanloop update` 只切换 CLI Release，不会同步 Workflow 配置。

改前/改后必须使用目标 Workflow 的真实 Stage/Step 拓扑和真实变化：绿色新增、红色删除、黄色表示改名、
重排或 executor 变化、灰色表示不变；不能只写数量。创建 Workflow 时，改前明确显示“当前不存在”。
Condition-first 使用真实 Route AND 组展示“哪些事实全部成立才能前进”，不使用抽象示例代替。

HTML 总长度不超过 500KB，适配飞书约 820px 文档区和手机宽度。避免嵌套卡片、文字溢出、装饰性渐变和
单一色调。视觉结构必须有明确阅读顺序，不能靠大段文字解释页面本身。颜色不能作为唯一变化标记，必须同时
显示新增、删除、调整、不变等文字。

## 交付到飞书

通用 ELI5 的 Sites 发布规则在这里替换为飞书 HTML Block 交付：

1. 使用 `manage-workflow-document` 把 HTML 嵌入 `workflow_document_url` 指向的同一份飞书文档。
2. 文档保持 `L2-内部`；不得改成公开访问，不得发布 Sites 或生成 ChatGPT 公网地址。
3. 每个 Requirement 只维护一个主审核 HTML Block。分析阶段写入需求和基线，构建阶段补齐精确候选，人工
   审核后锁定候选身份与已批准内容，发布阶段只能追加发布状态、链接和用户动作，不得改写已批准设计。
4. 每次写入后重新读取飞书文档，确认 HTML Block 存在，并取得真实 `block_id` 和 `revision_id`。
5. 用户的主要结果是飞书文档或 HTML Block 的 HTTPS 直达链接；本地 HTML 路径只是中间产物。
6. 修改同一 Requirement 时复用已有文档和对应 HTML Block；只有新的 Requirement 才创建新文档。
7. 嵌入、权限或回读失败时保持 blocked，报告真实阻塞，不得把本地文件或其他网址当成交付成功。
