# 定义技术问题

把来源材料、现状证据和目标之间的矛盾收敛为可审核的问题定义。事实尽量自行查明；无法查明的内容标记为开放问题，不把假设写成事实。

## 调查边界

1. 读取用户提供的需求、文档和上下文；仅在任务授权范围内检查代码、配置、指标或历史材料。
2. 说明业务形态、关键参与方、上下游和当前方案。评价旧方案时保持客观，解释其原始适用条件。
3. 用量化数据或可验证证据找出当前方案与目标的差距。没有数据时写明缺口、获取方式和负责人。
4. 收敛为 2–3 个核心问题。每个问题都必须同时给出：
   - 结论：具体哪里不满足目标；
   - 事实：数据、代码、配置、接口或来源链接；
   - 原因：事实如何导致该结论。
5. 固化目标、非目标、硬约束、成功指标和后续方案必须使用的评价维度。

## 产物

写入并回读 `.technical-solution/problem.md`，至少包含：

- 背景与业务特点；
- 当前方案及其适用边界；
- 事实与来源；
- 核心问题及因果链；
- 目标、非目标和约束；
- 验收指标与方案评价维度；
- 开放问题。

标题直接表达结论，避免“可用性”“架构优化”一类空泛标题。本 Step 不得出现候选方案、选型结论或目标架构。

文件完整、证据可追溯且开放问题不阻碍方案推导时，上报 `technical_problem_defined` 和 `problem_definition_path`。需要在当前 Step 重新整理时上报 `technical_problem_rework_requested`；仍能继续调查时只报告 progress。
