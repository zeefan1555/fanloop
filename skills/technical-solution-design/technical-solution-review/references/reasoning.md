# 用 What–Why–How 组织技术推导

每个重要问题或技术判断应形成可追溯的论证：

- **What**：正在解释的对象、问题、目标或决定是什么，范围是什么？
- **Why**：哪些事实和约束使它成立或值得做？涉及选型时，为什么选择这个方法，代价是什么？
- **How**：相关机制怎样工作，或计划怎样执行、检验，足以回应前面的问题吗？

以重要判断为单位，不要求每个自然段重复三问，也不要求出现三个固定标题或固定顺序。
相邻段落、表格、图和代码可以共同回答；项目标题和三级标题表达本段具体问题或结论。
当前九个二级语义章节的名称与顺序保持不变。

## 按当前步骤的职责展开

| 当前步骤 | 本步应解释的内容 | 尚不能替后续决定的内容 |
|---|---|---|
| 需求背景 | 业务在做什么，发生了哪些有证据的变化，现有链路如何运行 | 根因、目标值、新方案 |
| 核心问题 | 哪个差距值得解决，证据是什么，现有机制如何产生该问题 | 目标值、解决手段 |
| 设计目标 | 要达到什么结果，为何对应核心问题，如何判定达标与取舍边界 | 候选方案和技术选型 |
| 方案调研 | 候选是什么，如何满足同一组约束，各自机制、优势与代价是什么 | 最终总体架构 |
| 总体方案 | 核心决定是什么，为何选择它，组件职责和关键链路如何实现目标 | 局部难点的详细实现 |
| 难点解法 | 局部要解决什么，为何现有手段不够，正常、异常和恢复机制如何工作 | 未经批准的新总体选型 |
| 方案收益 | 声称什么效果，依据什么，如何测量与验证并区分已测和预期 | 未发生的结果与未经确认的归因 |
| 落地规划 | 要交付什么，为何这样分阶段，如何执行、验收、止损和恢复 | 新架构方向 |

论证可以由前后步骤逐步补全。本步只负责自己的事实和判断，不为凑齐 How 提前设计方案。
引用上游时指出具体结论或证据；仅写“详见背景”或给一个文件路径，不能代替承接关系。

## 让各个小闭环形成一篇完整方案

上层的 How 可以成为下一层继续解释的 What。例如“由变量依赖自动构图”是总体解法，后面再分别
解释如何声明依赖、为何静态构图、如何调度和合并子图。只展开读者理解或实施当前方案所需的层次。

每项关键手段向前回扣问题、目标或约束，向后落到机制与验证。跨章节的术语、取舍和数字口径须一致：
如果前文优先可读性，后文为并发牺牲可读性，应说明交换的条件、补偿和适用边界。
依赖上游没有提供的事实或因果关系时，回到最早受影响步骤补齐；成文不能自行补造理由。

事实支撑 Why，验证检验 How。区分逻辑成立、实际可行和效果已获得；方案能自圆其说不等于已被验证。
有数据则给来源、环境、时间、样本和统计口径；缺数据时给可核对的行为证据、缺口及验证办法。

从[范文索引](exemplars.md)按当前问题选读，在正式文档和本地图中定位三问的答案及承接关系：

| 范文位置 | 可学习的闭环 |

| [AI伴播](examples/ai-cohost-evolution/article.md)的“AI语音对话设计／AI语音链路优化” | 先为低时延缩短判停，再解释碎句问题与质量代价，后续由真实语音评测和判停机制承接 |

范文的具体事实和已知缺口以各篇导读为边界；历史数字、目录和图像风格不构成当前方案的标准答案。

## 审校必须分别回答三件事

1. **局部论证是否完整**：关键判断的 What、Why、How 能否在最终文档及其明确引用中找到？
2. **全文推导是否连贯**：各判断是否承接同一问题与目标，关键取舍是否一致，是否有脱离目标的手段？
3. **证据与验证是否成立**：事实、口径和图文是否一致，How 是否可执行和检验，目标是否冒充已测收益？

例如“采用缓存，因为要提升性能，通过 Redis 实现”只有措施与愿望，仍缺耗时定位、适用边界和验证依据。
标题齐全、固定三问齐全或局部理由自洽，都不能替代以上三项检查。

在既有 `review.md` 中覆盖全部重要判断；相同且有共同证据的判断可以归组。每项记录：

| 重要判断 | What／Why／How 的位置与内容 | 上下游承接与取舍 | 事实与验证依据 | 范文对照 | 差距、影响与最早受影响层 |
|---|---|---|---|---|---|

缺失写“缺失”，不适用给理由。上游片段只用于核验证据，不能替最终正文补答案。
局部论证、全文推导和证据验证分别给出结论；不以平均分抵消阻塞项，也不因没用三问标题而判失败。
阻塞标准与单项最早回流沿用审校 Skill；无需新增产物、Condition、状态或评分机制。
