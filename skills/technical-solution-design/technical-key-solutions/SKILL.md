# 设计难点解法

读取已批准的 `01-background.md` 至 `05-overall-solution.md` 和架构图。只选择真正决定目标能否达成的
2–4 个难点，按问题而非组件堆砌手段。

每个难点都写完整闭环：

- 要解决的业务特点、核心问题和目标指标；
- 定位证据与导致问题的具体机制；
- 采用的手段、关键流程、数据或状态变化；
- 涉及组件、接口、依赖及与总体架构的关系；
- 正常、异常、降级、恢复、幂等、一致性和资损保障；
- 代价、限制、失败边界及验证方法。

手段名称使用“体现特点的描述性定语 + 通俗后台术语”，例如“可恢复的低延时链路”，避免只有
“可用性”“性能优化”或生僻造词。数据和因果必须对应；不能只列措施后宣称效果。

将结果写入并回读 `.technical-solution/sections/06-key-solutions.md`。片段不得出现 Markdown 标题，
用加粗手段名、图表、时序或列表组织；不得静默改变核心模型、选型或总体架构。

发现上游变化时只上报最早受影响的 feedback Condition，并写清保留与失效范围；否则上报
`key_solutions_designed` 和片段路径。
