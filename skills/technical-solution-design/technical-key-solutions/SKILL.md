# 设计难点解法

开始前读取 [What–Why–How 推导标准](../technical-solution-review/references/reasoning.md)。

读取已批准的 `01-background.md` 至 `05-overall-solution.md` 和架构图。按独立问题识别真正决定目标
能否达成的难点，同源现象合并；从总体方案的关键机制继续展开，按问题而非组件堆砌手段。

先逐项判断接口、数据与存储、状态与并发、性能与容量、稳定性与观测、安全与合规、兼容与迁移
是否适用。只展开适用维度；不适用项写一句事实理由，不为凑模板制造伪问题。

每个难点都写完整闭环：

- 要解决的业务特点、核心问题和目标指标；
- 定位证据与导致问题的具体机制；
- 采用的手段、关键流程、数据或状态变化；
- 涉及组件、接口、依赖及与总体架构的关系；
- 正常、异常、降级、恢复、幂等、一致性和资损保障；
- 代价、限制、失败边界及验证方法。

手段名称使用“体现特点的描述性定语 + 通俗后台术语”，例如“可恢复的低延时链路”，避免只有
“可用性”“性能优化”或生僻造词。数据和因果必须对应；不能只列措施后宣称效果。

当文字和主架构图不足以解释关键闭环时，创建可编辑的
`.technical-solution/diagrams/<语义名称>.mmd`，并在本片段中引用精确路径；没有必要时不创建辅助图。

## 产物列表

以下逻辑产物均写入 `.technical-solution/sections/06-key-solutions.md`，必要辅助图沿用上述路径并由片段引用：

| 逻辑产物 | 完整性要求 |
| --- | --- |
| 关键机制设计 | 逐个难点说明问题、依据、机制、关键流程和验证方法，承接总体方案且披露代价与边界。 |
| 必要接口与数据模型 | 适用时说明关键接口、数据或状态变化及组件关系，足以解释机制如何运行。 |
| 异常与恢复设计 | 覆盖适用的失败、降级、恢复、幂等、一致性和资损保障，明确触发条件、处理及恢复结果。 |

逐项回读产物内容及引用的辅助图；接口、数据或异常恢复项不适用时写明事实理由。
片段不得出现 `#` 或 `##`；允许
按真实内容使用 `###`，但禁止 `####` 及手工 `1.1` 式标题。用加粗手段名、图表、时序或列表组织；
不得静默改变核心模型、选型或总体架构。

发现上游变化时只上报最早受影响的 feedback Condition，并写清保留与失效范围；否则仅在产物列表逐项完整时上报
`key_solutions_designed` 和片段路径。
