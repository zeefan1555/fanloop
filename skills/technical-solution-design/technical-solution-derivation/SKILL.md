# 推导技术方案

只使用已批准的 `.technical-solution/problem.md` 作为问题边界。先研究成熟产品、现有依赖和内部方案如何处理同类问题，再形成结论；无法取证的比较项标记为未知。

## 推导顺序

1. 从业务特点、目标和约束导出统一评价维度，例如延迟、吞吐、可用性、一致性、成本、复杂度、演进和交付风险。
2. 至少比较“不改”基线、可行内部方案和有证据的行业方案。所有方案使用同一组维度，公平写出优点、缺点、适用条件和失败边界。
3. 选择核心业务、数据、存储或交互模型；只讨论本问题真正需要的模型。
4. 给出推荐方向及明确取舍，解释为什么它比其他方案更适合当前业务特点，而不是只列功能。
5. 建立双向映射：每个核心问题至少对应一个设计决策，每个关键设计决策必须能回溯到问题、约束或指标。
6. 形成总体架构草图，标出上下游、层次、关键组件、主要数据/控制流及系统边界。

## 产物

写入并回读 `.technical-solution/proposal.md`，包含：

- 评价维度及其来源；
- 候选方案对比表；
- 推荐方向、核心模型与取舍；
- 问题—设计—预期效果映射；
- 总体架构草图与关键模块边界；
- 风险、未知项和需要人工确认的决策。

本 Step 不扩写最终叙事文档。问题基线未变化且推导完整时，上报 `technical_solution_derived` 和 `solution_proposal_path`；调查改变了已批准问题的语义时，上报 `technical_problem_changed` 并回流。
