# 确定需求背景

读取用户材料，并在授权范围内核对代码、配置、指标、历史文档和上下游信息。旧系统按其原始适用
条件客观描述，不使用“很差”“波动很大”等无证据判断。

调查并收敛三组事实：

1. 业务形态：关键场景、参与方、请求或资金特征、峰谷规律、账期及不可接受后果；
2. 现状架构：系统边界、上下游、核心组件、依赖、协议、数据流及已有保障；
3. 演进诉求：业务变化、当前基线、期望变化及时间窗口，但不提前写设计目标。

能量化时写具体口径，例如日常 QPS、峰值 QPS、倍数、P99、失败率、金额或容量，并附来源和时间
范围。暂时无法取证的内容标为“待确认”，写清获取方式，不把估算伪装成事实。

将结果写入并回读 `.technical-solution/sections/01-background.md`。片段中不得出现任何 Markdown
标题；使用加粗结论、短段落、表格和列表组织内容，以便最终原样放入“需求背景”。不得写核心问题、
目标、候选方案或目标架构。

证据完整且边界清楚时上报 `background_defined` 和片段路径。仍可继续调查时只报告 progress；已提交
背景需要重做时上报 `background_changed`。
