# 确定需求背景

开始前读取 [What–Why–How 推导标准](../technical-solution-review/references/reasoning.md)。本步说明
当前业务与系统是什么、为什么需要关注这次变化、现有机制如何支撑业务；后续方案的实现留给设计阶段。

读取用户材料，并在授权范围内核对代码、配置、指标、历史文档和上下游信息。旧系统按其原始适用
条件客观描述，不使用“很差”“波动很大”等无证据判断。

调查并收敛三组事实：

1. 业务形态：具体场景、参与方、关键链路、请求或资金特征、峰谷规律、账期及不可接受后果；
2. 现状架构：系统边界、上下游、核心组件、依赖、协议、数据流及已有保障；
3. 演进诉求：业务变化、当前基线、期望变化及时间窗口，但不提前写设计目标。

能量化时写具体口径，例如日常 QPS、峰值 QPS、倍数、P99、失败率、金额或容量。每项定量事实附
来源、时间范围和证据状态；证据状态只使用“现状事实/已测”“估算”“目标”“待确认”。暂时无法
取证的内容写清获取方式，不把估算、目标或待确认信息伪装成现状事实。

## 产物列表

以下逻辑产物均写入 `.technical-solution/sections/01-background.md`：

| 逻辑产物 | 完整性要求 |
| --- | --- |
| 背景与现状 | 交代业务变化、现状系统边界、上下游及当前机制，区分已有保障与演进诉求。 |
| 业务特点 | 明确具体场景、参与方、关键链路及影响本次需求的业务特征。 |
| 关键事实与证据 | 关键判断有可追溯来源；定量事实附时间、口径和证据状态，缺口有获取方式。 |

逐项回读产物内容，核对事实和边界。片段不得出现 `#` 或 `##`；允许
按真实内容使用 `###`，但禁止 `####` 及手工 `1.1` 式标题。使用加粗结论、短段落、表格和列表组织
内容，以便最终原样放入“需求背景”。不得写核心问题、目标、候选方案或目标架构。

仅在产物列表逐项完整且证据和边界检查通过时上报 `background_defined` 和片段路径。
仍可继续调查时只报告 progress；已提交
背景需要重做时上报 `background_changed`。
