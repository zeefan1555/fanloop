# Promotion Design Context

Promotion Design 是从碎片材料到 `require_points.md`、再到七段 `方案.md` 的统一写作 Skill。

## Language

**材料账本**：
保存用户原话、资料事实、语义角色、来源和覆盖结论的澄清工作态。
_避免_：聊天流水账、最终正文

**设计树**：
按前置依赖组织所有待用户决定事项的模型。
_避免_：无依赖问题清单、预先写死的访谈脚本

**Frontier**：
设计树中前置决策已确定、所需事实已查明、当前无需猜测即可回答的完整决策集合。
_避免_：随手挑选的一批问题、全部 Open Questions

**Grilling 轮次**：
合并本轮答案、重算设计树与 Frontier、一次问完整个 Frontier 并等待回答的循环。
_避免_：一问一答式追问、在同轮询问依赖当前答案的问题

**正向切片**：
从背景、问题、目标和业务特点向下推导场景约束、选型标准、调研、手段、效果和规划缺口。
_避免_：先有做法再包装目标

**反向切片**：
从调研、手段、效果或规划向上追溯其选型标准、场景约束、业务特点、问题和目标归属。
_避免_：按章节邻近或关键词猜测归属

**覆盖决策**：
把每条材料判定为吸收、合并、待确认或排除，并给出唯一落点或理由。
_避免_：把所有新信息直接追加进正文

**Requirement 基线**：
用户审核确认的 `require_points.md` 修订，是方案写作的唯一需求事实源。
_避免_：聊天记忆、brainstorm 工作态、未经确认的推导

**陌生评委冷读**：
只读取待审文档，验证不了解业务背景的评委能否复述项目、问题、目标、取舍、做法和结果。
_避免_：用作者口头补充解释文档缺口

## Relationships

- 每条新增材料先进入**材料账本**，再执行双向切片和**覆盖决策**，最后重新投影 Requirement 草案。
- 待决策项进入**设计树**；事实任务由 Agent 查明，只有真正的取舍进入 **Frontier**。
- 每个 **Grilling 轮次**必须询问完整 Frontier，并延后依赖本轮答案的节点。
- Frontier 为空不等于完成；事实任务和 Open Questions 也必须为空，用户还要明确确认共同理解。
- `require_points.md` 经语义连续性、陌生评委冷读和用户人审后，才成为**Requirement 基线**。
- `方案.md` 只能投影当前 Requirement 修订；Requirement 语义变化时旧方案立即过期。
- 任何手段都必须反向回扣选型标准、场景约束、业务特点、问题和目标；无法归属时保持待确认。
- 任何问题都必须正向推出目标和后续设计缺口；问题章节不得混入实现语言、工具或具体机制。
- 最终方案固定为“需求背景、问题、目标、方案调研、解决方案、效果、规划”，不展示设计树和内部编号。

## Example

> 用户：这个试点前端别人估两天，但我是第一次做，应该按四天暴露风险，而且倒排时不能直接接。
>
> Agent：先把“两天与四天”归为本项目的估时证据，把“不直接接”归为候选承诺门禁；再反向复核它们解决的容量承诺和风险决策问题。通用估时规则与承诺成立条件作为两个独立 Frontier 决策，不能把本项目的两倍经验直接推广成规则。
