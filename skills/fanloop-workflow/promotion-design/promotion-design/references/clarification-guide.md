# Promotion Requirement Clarification Guide

本文件是 Promotion Design 的需求澄清方法论事实源。目标只有一个：把多轮、乱序、多人参与的
讨论，持续沉淀成一份可审核的 `require_points.md`。聊天可以跳跃，Requirement 必须归位。

## 核心原则

1. `require_points.md` 是写方案前唯一事实源；先审核它，再写 `方案.md`。
2. 每轮先更新 `.promotion/brainstorm.md`，再回复用户。
3. 用户补充的每条内容都必须先进入材料账本，再归入背景、问题、目标、业务特点、外部支持、场景约束、选型标准、调研、候选手段、选定手段、效果、规划或待确认；禁止直接追加到最终文档。
4. “全部沉淀”指所有材料都有语义覆盖结论，不指逐字复制聊天。每条材料必须标记为吸收、与既有结论合并、待确认或有理由排除。
5. 全文必须通过[语义归位与推导连续性门禁](semantic-continuity-gate.md)；一句话只能有一个主语义角色，每个下游内容必须有上游来源。
6. 预览、落盘、确认和方案 Review 必须通过[陌生评委理解门禁](reviewer-comprehension-gate.md)，不得用聊天上下文替文档补背景。
7. 可见文档不使用内部字母编号、节点编号、机器映射表或聊天流水账。
8. 把待用户决定的内容组织成有依赖关系的决策树；每轮一次问完整个 Frontier，并为每题给推荐答案。
9. 事实由 Agent 使用文件、工具和已有资料查明；只把需要取舍的决策交给用户。
10. 每轮必须留下切片记录、上下文覆盖结论、决策树变化和 Frontier；没有记录，就没有完成澄清。

## 工作态

`.promotion/brainstorm.md` 至少维护这些块：

- `conversation_summary`：压缩后的对话事实，不粘贴长聊天记录。
- `raw_material_ledger`：用户原话、来源、材料类型和归位判断。
- `context_coverage`：每条材料的吸收、合并、待确认或排除结论，以及最终落点和影响范围。
- `requirement_draft`：按 `require_points.md` 结构持续更新的草案。
- `business_constraints`：业务特点、事实来源、场景约束、选型标准及其推导关系。
- `external_dependencies`：外部团队、系统、资源、政策和时间承诺，以及变化后的影响和兜底。
- `candidate_means`：用户提前提到但尚未完成回扣的手段、方案、工具和流程。
- `glossary`：内部术语、缩写和普通语言定义；未澄清术语不得进入已确认正文。
- `decision_ledger`：候选、统一选型标准、选择/放弃结论和证据来源。
- `design_tree`：全部待决策节点、前置依赖、状态、推荐答案及受影响 Requirement 章节。
- `frontier`：当前所有前置决策和事实均已解决、可以立即询问用户的决策节点。
- `fact_jobs`：Agent 可自行查明的事实及状态；事实未完成时只阻塞其下游决策。
- `decision_rounds`：每轮 Frontier、用户答案、树变化和新解锁节点。
- `evidence_ledger`：事实、数字、收益、个人贡献和来源。
- `reviewer_context`：答辩形式、规定时长、评委认知基线、陌生评委复述和首次困惑点。
- `open_questions`：所有未解决决策；用户可见回复只展示当前完整 Frontier。
- `slice_runs`：每轮切片记录，包含输入种子、正向切片、反向切片、合并决策和门禁结果。
- `review_state`：预览、人审意见、连续性发现、陌生评委理解发现、确认记录和阻塞项。
- `revision_state`：当前 Requirement 修订、方案所基于的修订及方案是否过期。
- `shared_understanding`：用户是否在 Frontier 清空后明确确认共同理解。

`slice_runs` 的每条记录必须包含：

```markdown
### Slice Run: <时间或轮次>

- 输入种子：
- 材料分类：
- 切片顺序：正向→反向 / 反向→正向
- 正向切片：
- 反向切片：
- 语义归位：
- 业务特点与约束影响：
- 推导断点与章节过渡：
- 陌生评委理解风险：
- 材料覆盖结论：吸收 / 合并 / 待确认 / 排除（含理由）
- 合并决策：
- 更新章节：
- 下游方案状态：未开始 / 保持有效 / 已过期
- 阻塞项：
- 本轮 Frontier：
- 延后节点及未满足依赖：
```

## 上下文输入与结构化投影

多轮讨论的所有信息只有一个去向：经过分析后沉淀到同一份 `require_points.md`。执行时借鉴
`techdesign` 的 Supporting Info Ledger、Glossary Challenge 和 Decision Ledger，并内化 `grilling`
的决策树与 Frontier 分轮追问；把
技术字段替换为 Promotion 的语义链，不引入 `PSM:Method`、字段映射或额外需求产物。

每轮按以下顺序处理：

1. **收件**：先把用户新增信息原样压缩进 `raw_material_ledger`，保留来源和时间，不能边听边改正文。
2. **原子化**：一句话同时包含背景、问题、目标和做法时，拆成多个材料项；每项只保留一个主语义角色。
3. **基线比较**：与当前 `requirement_draft` 对照，判断是新增、补证、细化、修改、删除、冲突还是纯表达。
4. **确定种子**：背景、问题、目标、业务特点和外部支持通常是上游种子；选型标准、调研、手段、效果和规划通常是下游种子。
5. **双向切片**：按种子方向先跑一侧，再跑另一侧，得到上游复核范围和下游重算范围。
6. **覆盖决策**：为每条材料写出四种结论之一。
7. **重新投影**：重写受影响章节，使整条论证链重新连贯；不得只在原段落末尾补一句。
8. **重算 Frontier**：只暴露前置决策和事实都已解决的全部节点，每题给推荐答案。
9. **准出**：更新门禁和修订号；Frontier 清空且用户确认共同理解后，完整 Requirement 才能进入人审。

四种覆盖结论：

| 结论 | 适用情况 | Requirement 处理 |
| --- | --- | --- |
| 吸收 | 形成新的已确认语义 | 写入唯一主章节，并同步重写受影响链 |
| 合并 | 与既有结论同义、补充细节或增强证据 | 合并到既有表述或证据，不制造重复条目 |
| 待确认 | 存在歧义、冲突、缺少来源或会推翻既有基线 | 写入待确认和决策树，不伪装成事实 |
| 排除 | 与项目无关、重复且无新增信息，或用户明确撤回 | 记录排除理由，不能静默丢弃 |

覆盖完成标准：`raw_material_ledger` 中每条材料都能在 `context_coverage` 找到结论；所有“吸收”和
“合并”项都能指向 `require_points.md` 中的明确章节；所有“待确认”项都在 `open_questions`；所有
“排除”项都有可审核理由。工作态保留逐条映射，`require_points.md` 的覆盖检查按同义语义簇合并，
并在每次修订时重算，不能演变成按聊天轮次追加的流水账。

## 外部支持与依赖变化

外部团队支持、接口能力、资源额度、政策、排期、负责人承诺或上下游系统状态发生变化时，不能
直接修改 `方案.md`。它们通常会改变方案成立前提，因此必须作为 Requirement 变更种子处理：

1. 先记录旧前提、新事实、来源、生效时间和确定性；
2. 反向确认它原本支撑哪个背景事实、业务特点、场景约束、选型标准或手段；
3. 正向重算受影响的问题后果、目标边界、候选比较、选定手段、效果口径和规划；
4. 不受影响的章节保留，受影响章节重新投影，冲突内容进入待确认；
5. 生成新的 `require_points.md` 修订并重新通过双门禁和用户审核；
6. 旧 `方案.md` 标记为过期，只能基于新修订重新生成或更新。

外部变化没有实际影响时，也必须在切片记录中说明为什么依赖链在该节点终止，不能凭感觉判定
“方案不用改”。

## 决策树与 Frontier 分轮追问

把需求澄清建模为决策树。每个决策节点至少记录：决策内容、依赖节点、当前状态、用户答案、Agent
推荐答案、依据和受影响的 Requirement 章节。内部节点可使用稳定标识，但不得把标识和树结构写进
最终读者正文。

Frontier 是所有“前置决策已经确定、所需事实已经查明、现在无需猜测即可回答”的未决节点。每轮：

1. 合并用户本轮回答，更新已确定节点和 Requirement 草案；
2. 运行正向、反向切片，新增、删除或重连受影响决策节点；
3. 用文件、工具和已有资料查明事实；有子 Agent 能力时并行派发独立事实探索，不向用户询问可自行获取的信息；
4. 事实检索未完成时，只阻塞依赖它的节点，其他独立节点照常进入 Frontier；
5. 重算 Frontier，一次问完其中所有决策；
6. 每题编号，给出推荐答案和简短理由；发问后停止推进，等待用户回答；
7. 依赖本轮答案的问题必须留到下一轮，不能用假设答案提前追问。

统一问题格式：

```text
❓ **Q1** - **<问题标题>**: <问题正文；必要时给出互斥选项>

➡️ <推荐答案及简短理由>
```

用户可以逐题回答、批量接受推荐答案或修改任意一题。每轮答案都会重塑决策树，必须重新切片和
计算 Frontier，不能沿用上一轮预先准备的问题列表。

Frontier 为空只有两种可能：

- 仍有事实任务或被阻塞节点：澄清未完成，继续查明事实；
- 所有分支均已访问、Open Questions 为空且没有静默假设：展示共同理解和 Requirement 预览，要求
  用户明确确认。

用户未明确确认共同理解前，不得落盘最终 Requirement、生成 `方案.md` 或执行其他下游动作。

## 四阶段推进

### Phase 1/4 · INTAKE

把讨论归位到项目边界和需求背景。

必须确认：

- 项目是谁负责的、在什么周期内发生、当前是否已经上线或仍在规划；
- 作者负责边界和协作边界；
- 评审者应该看到的核心能力；
- 答辩形式、规定时长，以及评委可以默认知道和不能默认知道的内容；
- 背景事实和材料来源；
- 可能影响选型的业务特点及其事实来源；
- 不做范围和还缺哪些材料。

如果用户先讲“我做了某个平台/流程/机制”，把它放入 `candidate_means`，再反问它为什么在当时必须做。

### Phase 2/4 · EVENTS

对齐 `techdesign` 的 EVENTS 阶段，把讨论归位到项目事实事件和证据事件。Promotion 的事件不是
技术领域事件，而是晋升材料里的关键发生点。

必须确认：

- 背景事件：业务、系统、流程或协作怎样演进到当前状态；
- 痛点事件：风险、低效、不一致、不可控、成本高、稳定性不足或协作阻塞在哪里发生；
- 决策事件：做过哪些关键判断、调研或取舍；
- 执行事件：做了哪些平台、流程、机制、工具、系统或协作动作；
- 结果事件：上线范围、指标变化、复用、稳定性、效率、影响面和反馈；
- 证据来源：每个事件来自用户原话、文档、代码、指标、复盘还是会议。

事件阶段只做拆解和归位，不写最终问题、目标或手段。用户提前说出的“平台、工具、治理、机制”
属于执行事件，后续在 FEATURES 阶段再判断它是不是候选手段。

### Phase 3/4 · FEATURES

对齐 `techdesign` 的 FEATURES 阶段，把 EVENTS 中的事实事件收敛成 Requirement 的可审核要素。
Promotion 的 feature 不是接口功能点，而是问题、目标、调研结论、候选手段、选定手段和证据契约。

必须确认：

- 三项问题，每项都来自痛点事件，并包含背景、事实、后果；
- 三项目标，每项都回应一个问题，并包含验收口径；
- 业务特点是否项目特有、有证据且实际改变选择空间；
- 每项业务特点和目标推出哪些硬/软场景约束、阈值和边界；
- 场景约束怎样转成统一的选型标准、优先级和淘汰条件；
- 一到三项真正影响选型的调研；
- 候选手段分别服务哪些目标、覆盖哪些问题；
- 所有候选怎样按同一组选型标准比较，为什么选择当前手段并放弃其他手段；
- 每个选定手段的责任人、触发、输入、动作、输出证据、验收标准和异常处理。

用户如果继续补充新手段，不直接加入最终手段。先跑反向分析：它解决哪个问题，服务哪个目标，
需要补充哪个背景事实，是否推翻已有目标或选型。

### Phase 4/4 · CLARIFY

把工作态投影成 `require_points.md`，并完成审核前准出。

必须通过：

- 背景、问题、目标、业务特点、场景约束、选型标准、调研、候选手段、选定手段、效果和规划均归位；
- 问题和目标各三项，且逐项呼应；
- 每个手段都经过选型标准和场景约束回扣业务特点、问题和目标；
- 每个调研都影响选型；
- 每个场景约束都有特点或目标来源，每个候选都使用同一组选型标准比较；
- 全文已执行语义归位与推导连续性门禁，错位、断点、跳跃、悬空和过渡缺失均为零；
- `require_points.md` 已在不读取聊天和工作态的条件下通过陌生评委理解门禁；
- 所有推导项得到用户确认；
- Open Questions 为空。

未通过时只能输出草案和阻塞项，不能进入 `方案.md` 写作。

## 切片流水线

Promotion Design 抄 `techdesign proposal` 的机制，而不是抄它的技术字段：

```text
require_points 草案和用户新材料
  ↓
双向切片：
  上游种子 → 正向推导下游，再反向复核
  下游种子 → 反向寻找归属，再正向重放
  ↓
合并归位：标注来源并更新同一份 requirement_draft
  ↓
门禁：能否预览、落盘、人审、写方案
```

对应关系：

| techdesign proposal | Promotion Design |
| --- | --- |
| `require_point.md` 的 PSM:Method | `require_points` 草案中的背景、问题、目标 |
| 正向变更分析 | 从问题目标推导调研、手段、效果和规划缺口 |
| 反向影响面切片器 | 从新增手段、效果、规划反推归属和上游影响 |
| `[正向] / [反向推导]` | `正向切片 / 反向切片 / 用户确认` |
| `proposal.md` | `require_points.md` |
| proposal review | Requirement 人审 |

每轮都跑完整流水线；没有新增内容的一侧也要写“无新增影响”，这样才能保证机制被使用。

输入种子决定先分析哪个方向，但不改变双向门禁：背景、问题、目标、业务特点属于上游种子，先
正向推导再反向复核；场景约束、选型标准、调研、手段、效果、规划属于下游种子，先反向归属再从
确认的上游正向重放。正文始终按背景、问题、目标、业务特点、场景约束、选型标准、调研、手段、
效果、规划的顺序投影。

## 正向切片

正向切片用于“从上往下”发现缺口。每轮都执行，尤其是背景、问题或目标变化后。

输入：

- 已确认背景；
- 已确认问题；
- 已确认目标；
- 已确认业务特点及其事实来源；
- 已确认评审重点和个人边界。

动作：

1. 从背景检查问题是否真实存在：这个问题是否由背景事实自然产生。
2. 从问题检查目标是否必要：目标是否直接缓解该问题，而不是另起炉灶。
3. 从目标和业务特点检查场景约束：哪些硬/软条件、阈值和边界限制选择空间。
4. 从场景约束形成选型标准：候选应按哪些维度比较，什么条件直接淘汰。
5. 从选型标准检查调研和候选：是否使用同一标准比较，是否遗漏可行路径。
6. 从调研取舍检查手段：结论是否自然推出当前做法，而不是突然罗列实现。
7. 从手段检查效果口径：手段完成后留下什么证据，如何证明目标被推进。
8. 从未完成目标、残余风险和依赖检查规划：规划是否来自前文尚未闭合的内容。

产出：

- 需要补充的问题候选；
- 需要补充的目标候选；
- 需要追问的调研或取舍；
- 需要确认的业务特点、场景约束和选型标准；
- 需要下钻的手段契约；
- 下一轮可进入 Frontier 的决策候选及其依赖。

完成标准：

- 已说明本轮上游内容是否改变；
- 已说明每个问题是否仍由背景支撑；
- 已说明每个目标是否仍回应问题；
- 已说明下游调研、手段、效果或规划是否有缺口；
- 已说明相邻层级是否存在推导断点或跨层跳跃；
- 候选项已标注待确认，未伪装成用户原话。

## 反向切片

反向切片用于“从下往上”归位用户后续补充的新手段、新效果或新规划。每轮都执行，尤其是用户说
“还做了一个方案/工具/机制/平台/流程/指标/规划”时。

输入：

- 用户新补充的手段、效果、调研或规划；
- 当前 `requirement_draft`；
- 当前 `candidate_means` 和 `evidence_ledger`。

动作：

1. 判断新内容类型：手段、效果、调研、规划、背景事实、问题、目标或纯表达。
2. 如果是手段，反推它满足哪个选型标准和场景约束、来自哪个业务特点、服务哪个目标、解决哪个问题、依赖哪个背景事实。
3. 如果是效果，反推它验证哪个目标、由哪些手段带来、是否能归因到作者。
4. 如果是调研，反推它影响哪个选型结论，不能只作为参考列表。
5. 如果是规划，反推它来自哪个未完成目标、残余风险或外部依赖。
6. 如果找不到上游归属，放入候选或待确认，不能塞进不匹配的章节。
7. 如果它推翻已有问题、目标或选型，标记为“影响上游”，新增高优先级决策节点并按依赖进入 Frontier。

产出：

- 可直接归位的章节；
- 需要补充或修改的上游章节；
- 保持不变的章节；
- 阻塞项、可进入 Frontier 的决策及其依赖。

判断规则：

- 新手段能经过既有选型标准和场景约束回扣业务特点、问题和目标：补入候选手段或选定手段。
- 新手段需要新增业务特点、场景约束、选型标准、问题或目标：先问用户是否补充上游，确认后再修改。
- 新手段只是更细的执行方式：补入对应手段的输入、动作、输出、异常处理。
- 新效果没有证据来源：进入效果待确认，不进入已确认收益。
- 新效果改变目标口径：先改目标，再改效果。

完成标准：

- 已判断用户新内容是不是下游种子；
- 每个下游种子都有上游归属或待确认原因；
- 手段不能只回扣目标，还必须经过选型标准和场景约束回扣业务特点；
- 需要修改上游时，没有直接改最终 Requirement，而是进入决策树或待确认；
- 无法归属的内容保留在候选或开放问题，没有塞进问题章节。

## 合并归位

正向切片和反向切片完成后，必须合并到同一个 `requirement_draft`，不创建第二份草案。

合并顺序：

1. 先合并已确认事实和用户原话背后的稳定语义，不复制聊天句式。
2. 再合并正向切片推出的待确认缺口。
3. 再合并反向切片定位到的候选手段、效果或规划。
4. 若反向切片要求修改上游，先把上游改动放入待确认，不落盘。
5. 更新每条材料的吸收、合并、待确认或排除结论。
6. 重新投影全部受影响章节，不能只在末尾追加补丁句。
7. 最后更新 `open_questions`、决策树、Frontier、修订状态和方案新鲜度；Frontier 内按风险排序。

合并完成标准：

- 每条新材料只有一个主归位章节；
- 跨章节影响被写进切片记录，而不是复制到多个章节；
- 材料账本与上下文覆盖结论逐项对齐，没有未处理输入；
- `candidate_means` 中无法归属的手段没有进入选定手段；
- `requirement_draft` 仍保持背景、问题、目标、业务特点、场景约束、调研、手段、效果、规划顺序。
- 全文重新执行语义归位与推导连续性门禁后仍为零发现。
- Requirement 发生语义变化时，修订号已递增，旧人审结论和下游方案已失效。

## 门禁状态

每轮合并后必须给出一个门禁状态：

| 状态 | 含义 | 允许动作 |
| --- | --- | --- |
| `collecting` | 仍在收集背景、问题或目标 | 继续 Frontier 分轮追问 |
| `slicing` | 有候选手段或效果正在找归属 | 继续正反向切片 |
| `previewable` | 可生成草案预览，但仍有待确认项 | `pd 预览` |
| `reviewable` | Frontier、Open Questions 和事实任务为空，用户已确认共同理解 | `pd 落盘` |
| `approved` | 用户确认 Requirement | `/promotion design` |

不得从 `collecting`、`slicing` 或 `previewable` 直接进入方案写作。

## 每轮回复格式

每轮回复保持短，但必须包含：

- 当前阶段；
- 已经把用户新材料归到哪里；
- 正向切片结论；
- 反向切片结论；
- 当前门禁状态；
- 下一步；
- 当前完整 Frontier，每题带推荐答案。

示例：

```text
当前在 Phase 3/4 · FEATURES。我把“自动化巡检平台”先归到候选手段。正向切片发现效果证据和
运行边界仍缺失，反向切片确认它可能覆盖风险发现滞后。当前 Frontier 有两个互不依赖的决策：

❓ **Q1** - **效果证据**: 平台最直接留下哪类可验证证据？

➡️ 推荐使用风险发现提前量和人工排查耗时，因为两者分别对应时效与成本目标。

❓ **Q2** - **运行边界**: 首期是否只覆盖高风险变更？

➡️ 推荐先覆盖高风险变更，以较小范围验证误报率和处置闭环。
```

## 预览与落盘

`pd 预览`：

- 从 `.promotion/brainstorm.md` 生成 `require_points.md` 预览；
- 不覆盖已确认文件；
- 明确列出阻塞项、待确认项和可进入人审的程度。
- 附上陌生评委六句话复述和第一个困惑点；没有规定时长时标记“时间适配待验证”。

`pd 落盘`：

- 只有 Phase 4 准出通过才覆盖写入 `require_points.md`；
- 决策树所有分支必须已访问，Frontier、Open Questions 和未完成事实任务均为空；
- 用户必须明确确认已达成共同理解；
- 只能覆盖同一份 `require_points.md`，不得创建 `require_points_new.md`、`require_points_final.md` 等平行版本；
- 本轮材料账本与上下文覆盖结论必须逐项对齐；
- 陌生评委理解门禁必须通过，答辩形式和规定时长必须已确认；
- 同时归档当前 `.promotion/brainstorm.md`；
- 提示用户先审核 Requirement，而不是直接写方案。

## 人审门禁

用户审核 `require_points.md` 时，任何反馈都先判断影响范围：

- 影响背景、问题、目标、业务特点、场景约束、选型标准、调研或选型：回到对应 Phase 更新 Requirement。
- 只影响手段细节：更新对应手段契约，再重新跑反向分析。
- 影响外部支持、依赖、资源、排期、政策或协作承诺：按上游变更种子重新切片，旧方案立即标记为过期。
- 只影响措辞：可直接改 Requirement 文案，但不能改变含义。

交给用户审核前必须按[语义归位与推导连续性门禁](semantic-continuity-gate.md)完成逐句归位、
正向推导、反向追溯和章节过渡检查；任何发现都是阻塞项，不能以“用户后续会审核”为由放行。

随后按[陌生评委理解门禁](reviewer-comprehension-gate.md)只读取当前 `require_points.md` 做冷读；
复述失败、背景依赖聊天、术语前置、时间线堆叠、贡献模糊或时长未确认时，同样不能放行。

用户在 Frontier 清空后明确确认共同理解，并审核当前修订的 `require_points.md`，才进入
`/promotion design`。方案必须记录它所消费的
Requirement 修订；两者不一致时，禁止继续方案 Review。
