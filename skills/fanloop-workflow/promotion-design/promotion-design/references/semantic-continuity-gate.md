# 语义归位与推导连续性门禁

本门禁解决两类问题：一句话放错层级，以及内容虽然放在正确章节却突然出现、没有推导过程。
它用于 Requirement 澄清、方案生成和 Review，检查对象是整条论证链，不是某个技术词。

## 语义层级

每句话必须只有一个主语义角色，并放在对应章节：

| 层级 | 回答的问题 | 可以写 | 不应写 |
| --- | --- | --- | --- |
| 背景 | 为什么现在需要关注 | 已发生事实、环境变化、边界、已有约束 | 未来准备采用的做法 |
| 问题 | 当前哪里存在差距 | 事实、矛盾、风险、不解决的后果 | 解决动作、方案名称、实现选择 |
| 目标 | 问题解决后应是什么状态 | 可观察状态、验收口径、不做边界 | 平台、工具、流程或技术选型 |
| 业务特点 | 这个业务有什么项目特有事实 | 规模、频率、时效、风险、合规、环境、用户与协作特点 | 通用质量口号、未来实现偏好 |
| 场景约束 | 这些特点怎样限制选型 | 硬/软约束、阈值、运行与协作边界 | 没有业务来源的技术偏好 |
| 选型标准 | 候选应该怎样统一比较 | 比较维度、优先级、验证方式、淘汰条件 | 为某个候选量身定做的标准 |
| 调研与取舍 | 哪个候选最符合目标和约束 | 候选、同标准比较、借鉴、妥协、放弃理由 | 没有结论的资料罗列 |
| 手段 | 具体怎样推动目标 | 选定方案、机制、流程、架构、实现动作 | 无上游来源的功能清单 |
| 效果 | 如何证明目标被推进 | 指标、事实、证据、验证方式、归因边界 | 没有目标或手段来源的收益 |
| 规划 | 哪些未闭合内容继续处理 | 未完成目标、残余风险、依赖和准出证据 | 与前文无关的愿望清单 |

一句话若同时包含两个角色，必须拆开。例如“人工判断分散，因此建设统一平台”包含问题和手段：
前半句留在问题，后半句进入候选手段；不能因为有“因此”就把两个层级塞在一起。

过渡句可以引用相邻两层，但主角色只能是说明二者关系，不能借过渡句引入尚未完成调研和取舍的
新手段。

技术名词本身不是错误。描述当前系统事实时可以出现在背景或问题；指定未来如何实现时属于调研、
取舍或手段。判断依据是句子的语义角色，不是关键词。

业务特点也不是所有项目都成立的通用愿望。“高可用、易维护、性能好”本身不是业务特点；只有
说明具体业务事实、证据，以及它怎样改变候选选择时，才进入业务特点。团队熟悉某种技术属于
组织约束，不得包装成业务特点。

## 双向连续性检查

### 正向分析：证明为什么会走到这里

沿全文从上向下检查：

```text
背景 → 问题 → 目标
  └→ 业务特点
目标 + 业务特点 → 场景约束 → 选型标准 → 调研与候选比较 → 手段 → 效果 → 规划
```

逐层回答：

1. 哪个背景事实自然产生了这个问题？
2. 这个目标具体消除或缓解哪个问题？
3. 哪些有证据的业务特点会影响如何达成目标？
4. 每个特点和目标分别推出什么硬/软场景约束、阈值和边界？
5. 场景约束怎样转成可比较的选型标准和淘汰条件？
6. 调研和候选比较为什么推出当前手段，而不是另一个候选？
7. 手段完成后留下什么证据，如何验证目标被推进？
8. 哪个未完成目标、残余风险或依赖推出后续规划？

相邻层级没有回答连接问题就是“推导断点”；从问题直接跳到具体手段，或从泛化特点直接跳到
技术选型而没有场景约束、选型标准和候选比较，
就是“跨层跳跃”。章节齐全但连接问题答不出来，仍然不能通过。

### 反向分析：证明突然出现的内容属于这里

从每个手段、效果和规划向上追溯：

- 手段必须回到候选比较、选型标准、场景约束、业务特点、目标、问题和必要背景；
- 效果必须回到产生它的手段和被验证的目标；
- 规划必须回到未完成目标、残余风险或外部依赖；
- 找不到上游归属的内容是“悬空内容”，只能进入候选或待确认。

用户先讲背景、问题、目标或业务特点时，先正向分析下游缺口，再用反向分析复核新增内容有没有
归属。用户先讲场景约束、选型标准、手段、效果或规划时，先反向分析找到上游，再从已确认上游
正向重放整条链。无论输入顺序如何，同一轮都必须完成两个方向。

## 叙事过渡检查

推导关系成立后，再检查读者是否能看到这条关系。每个章节开头或结尾必须用自然语言承接相邻层级：

- 背景收束到需要解决的矛盾；
- 问题收束到需要达到的状态；
- 目标引出必须验证的约束和候选路径；
- 业务特点推出场景约束，场景约束转成选型标准；
- 调研使用同一组选型标准比较候选并给出明确取舍，随后才展开选定手段；
- 手段引出可验证证据；
- 效果中的未闭合项引出规划。

过渡不要求固定句式，也不要求添加空泛连接词。只写“因此”“基于以上分析”但没有复述上文结论
和下文选择依据，仍是“过渡缺失”。

## 发现与修复

Review 必须先列完以下发现，再给总体判断：

```text
[阻塞·语义错位 | 推导断点 | 跨层跳跃 | 业务脱节 | 悬空内容 | 过渡缺失] <章节 / 小标题>
原文：<完整句子或相邻段落>
当前角色：<它实际上在回答什么>
应归位：<正确层级>
正向检查：<缺少哪一层或哪条连接>
反向检查：<能否追溯到上游；不能时说明缺口>
修复：<拆分、迁移、补充取舍或增加实质过渡；无法可靠修复时写“需要作者确认”>
```

修复错位内容时必须保留语义：先从错误章节移出，再放入正确章节或候选区；不能为了让上游看起来
干净而删除用户提供的手段。修复推导断点时补的是缺失判断，不是补一个连接词。

## 准出标准

- 每句话都有且只有一个主语义角色，并位于对应层级；
- 每个下游内容都能反向追溯到上游，悬空内容为零；
- 每条受影响链都完成正向分析，相邻层级无断点，跨层跳跃为零；
- 每个选定手段都能经过选型标准和场景约束回扣业务特点，“业务脱节”为零；
- 读者能从章节文字中看到真实过渡，过渡缺失为零；
- 无法归位或无法补齐的内容全部进入待确认。

任一条件不满足时，Requirement 不得进入 `reviewable` 或 `approved`，`方案.md` 不得判为 Review
通过。
