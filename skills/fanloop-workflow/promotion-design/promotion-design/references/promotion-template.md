# <一句话讲清方案价值的标题>

本方案必须基于已确认的 `require_points.md` 和证据材料生成。若写作过程中发现新的背景、问题、
目标、选型或个人贡献边界，先回到 Requirement 澄清更新 `require_points.md`，不得在方案正文中
静默补齐。若 Requirement 修订号与本文 `require_points_revision` 不一致，本文视为过期，必须先
完成新修订的双向切片、双门禁和用户审核，再重写受影响章节。

<用一个不依赖内部背景的开场摘要讲清：这是什么项目、为什么现在必须做、作者负责什么、核心
问题与判断是什么、当前结果或验证方式是什么。每节先给结论，再给必要证据和关键细节；首次出现
的内部术语必须用普通语言解释。>

用连贯叙事说明业务或能力如何演进到当前形态、当前系统负责什么，以及为什么现在需要继续
演进。只保留理解问题所需的既有事实和硬约束；未来技术选择、团队偏好和准备采用的做法放到
方案调研或解决方案。结尾收束出当前必须解决的矛盾，再进入问题。阶段、角色或组件关系较多时，
在这里加入必要图示。不能要求评委预先知道内部系统、组织分工或历史事件。
