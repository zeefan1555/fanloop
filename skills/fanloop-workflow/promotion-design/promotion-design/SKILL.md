# Promotion Design

> 从碎片项目材料到可评审晋升方案的阶段式写作工作流。默认统一澄清链路，先把
> `require_points.md` 写好，再生成 `方案.md`，最后审校事实、贡献、价值和表达。

本 Skill 由 `promotion-design` Workflow 的 Agent Step 调用。它只维护 Promotion 领域产物，
不推进流程状态；唯一流程状态由 Fanloop 的 `.fanloop/flow/state.json` 管理。

需求澄清强制使用本 Skill 内化的 Grilling 机制，不再调用 `batch-grill-with-docs`：把所有待决策项
组织成有依赖关系的设计树，逐轮询问完整 Frontier，事实由 Agent 自行查明，决策由用户确认；
Frontier 清空后仍须用户明确确认共同理解。以下热路径和 clarification guide 已完整承载该机制，
不能把它降级成一次性问题清单或自由对话。

详细澄清方法、正向切片、反向切片、预览/落盘和人审门禁以
[`references/clarification-guide.md`](references/clarification-guide.md) 为唯一事实源。普通轮次先读
本文件的热路径；进入澄清执行时必须读取 clarification guide。

## 热路径

1. `clarify_requirements` 每轮先把新增上下文写入 `.promotion/brainstorm.md` 的材料账本和决策树；不得把用户新话语直接追加进 `require_points.md` 或 `方案.md`。
2. 用户可以乱序讲背景、问题、目标、业务特点、外部支持、场景约束、调研、手段、效果和规划；Agent 必须拆成原子材料并归位，不能按用户讲述顺序写 Requirement。
3. 每条新增材料都必须经过双向切片并更新决策树；每轮重算 Frontier，一次问完所有前置条件已满足的决策，每题给推荐答案，依赖本轮答案的问题留到下一轮。
4. 任何 `requirements_ready`、`promotion_design_written` 或 Review Result 上报前，必须同时执行[语义归位与推导连续性门禁](references/semantic-continuity-gate.md)和[陌生评委理解门禁](references/reviewer-comprehension-gate.md)。
5. `require_points.md` 是唯一需求澄清基线；任何语义变更都由 Workflow 回流到 `clarify_requirements`，再生成或更新 `方案.md`。

## 强制切片流水线

每个澄清轮次都按同一个流水线执行，不能跳过：

```text
用户新材料
  ↓
原子化并分类：背景 / 问题 / 目标 / 业务特点 / 外部支持 / 场景约束 / 选型标准 / 调研 / 手段 / 效果 / 规划 / 待确认
  ↓
双向切片：
  上游种子 → 正向推导下游，再反向复核
  下游种子 → 反向寻找归属，再正向重放
  ↓
覆盖决策：吸收 / 合并 / 待确认 / 排除
  ↓
重新投影：按受影响链更新同一份 requirement_draft，不做句尾追加
  ↓
更新决策树并自行查明可获取事实
  ↓
重算 Frontier：一次问完所有当前可决策问题，并给推荐答案
  ↓
等待用户回答，再进入下一轮
```

本轮完成标准：

- `.promotion/brainstorm.md` 已记录用户新材料的归位分类；
- 已记录输入属于上游还是下游，以及本轮先正向还是先反向；
- 已记录正向切片结果，即使结论是“本轮无新增下游缺口”；
- 已记录反向切片结果，即使结论是“本轮无新增上游影响”；
- 已记录每条材料的覆盖决策：写入哪个 Requirement 章节、与什么结论合并、保留为待确认，或为何排除；
- 新材料已得到唯一主归位，受影响推导链没有断点或跨层跳步；
- 已更新决策树及依赖边，并重算当前 Frontier；
- 用户可见问题恰好覆盖整个 Frontier，没有追问依赖本轮答案的下游节点；
- 可由文件、工具或已有资料查明的事实由 Agent 自行查明，没有转问用户；
- 若已有 `方案.md`，已判断它是否因 Requirement 变化而失效；
- 每个 Frontier 问题都包含推荐答案，发问后停止推进并等待用户回答。

缺少任一项，本轮澄清未完成，不得声称已更新 Requirement。

## 工作目录

每个 Promotion 项目的产物固定落在 Requirement Root：

```text
<requirement-root>/
├── .promotion/
│   ├── brainstorm.md
│   └── review.md
├── require_points.md
├── evidence.md
└── 方案.md
```

`.promotion/brainstorm.md` 是唯一领域中间文件，使用 YAML front matter 加 Markdown 展示即可。
`evidence.md` 可选，用于记录事实、指标、链接、个人贡献边界和待确认材料；没有证据时不能补写数字或因果。
审校结果固定写入 `.promotion/review.md`。
不得创建 `.promotion/state.json` 或用领域文件推断当前 Step；准出、回流、Output 失效与人工确认只读取 Fanloop Status。

## 四阶段流程

```text
Phase 1/4 · INTAKE     项目边界与需求背景
Phase 2/4 · EVENTS     项目事实事件与证据事件
Phase 3/4 · FEATURES   问题、目标、业务约束、选型与证据契约
Phase 4/4 · CLARIFY    Requirement 归位、准出和确认
        ↓
require_points.md      用户审核
        ↓
write_promotion_design 生成或更新 方案.md
        ↓
review_promotion_design 晋升材料审校
```

### Phase 1/4 · INTAKE

目标是确认“这是谁的什么项目，为什么现在要写，评审者应该看到什么”。本阶段只追问最阻塞的
背景问题，不急着定方案。

必须沉淀：

- 项目名称、业务/技术领域、时间范围和当前状态；
- 作者角色、负责边界、协作方和不能归因到个人的部分；
- 晋升目标或评审语境，例如技术深度、复杂度、影响面、方法沉淀；
- 答辩形式、规定时长、材料阅读方式，以及评委可以默认知道和不能默认知道的内容；
- 需求背景：业务或能力如何演进到当前状态，当前系统/流程负责什么，为什么需要继续演进；
- 初始业务特点：服务对象、规模、频率、时效、风险、合规、运行环境、使用习惯和协作方式中真正影响设计的事实；
- 外部支持与依赖：协作团队、上下游系统、资源、政策、排期和承诺，以及不成立时的影响；
- 已有资料来源：文档、代码、指标、复盘、会议纪要、图表和用户口述；
- 明确不做范围和材料缺口。

用户如果先讲“我做了某某平台/方案/工具”，先记录为候选事实或候选手段，再追问它解决的背景
和评审语境。不得把“做了什么”直接写成“为什么要做”。

### Phase 2/4 · EVENTS

对齐 `techdesign` 的 EVENTS 阶段：先不写最终问题和手段，而是把项目讨论拆成可追溯的事实事件。
Promotion 里的事件不是系统领域事件，而是晋升材料里的关键发生点、决策点和证据点。

必须沉淀：

- 背景事件：业务、系统、流程或组织协作怎样演进到当前状态；
- 痛点事件：哪里出现了风险、低效、不一致、不可控、成本高或协作阻塞；
- 决策事件：何时做过关键判断、放弃过什么方案、为什么转向当前路径；
- 执行事件：实际做了哪些平台、流程、机制、工具、系统或协作动作；
- 结果事件：上线范围、指标变化、复用、稳定性、效率、影响面和反馈；
- 证据来源：每个事件来自用户原话、文档、代码、指标、复盘还是会议。

归位规则：

- 痛点事件后续才归纳为问题，不直接把事件原话塞进问题章节；
- 执行事件后续才归纳为候选手段，不出现在问题章节；
- 结果事件后续才归纳为效果证据，不能倒推虚构目标；
- 决策事件后续进入方案调研和取舍，不作为最终方案清单；
- 一个用户输入可以拆成多个事件，但每个事件必须有来源。

### Phase 3/4 · FEATURES

对齐 `techdesign` 的 FEATURES 阶段：把 EVENTS 中的事实事件收敛成 Requirement 的可审核要素。
Promotion 里的 feature 不是接口功能点，而是问题、目标、业务特点、场景约束、选型标准、调研
结论、候选手段、选定手段和证据契约。

必须沉淀：

- 三个问题簇：从痛点事件归纳，每个问题都包含背景、事实和后果；
- 三个目标：分别回应三个问题，包含可观察状态、验收口径和边界；
- 业务特点：有来源、项目特有且实际影响选型的业务事实；
- 场景约束：由业务特点和目标推出的硬约束、软约束、阈值与边界；
- 选型标准：把场景约束转成可比较维度、优先级和淘汰条件；
- 一到三个真正影响选型的调研对象、历史方案或同类系统；
- 每项调研说明它解决什么、可借鉴什么、不能照搬什么、给本项目带来什么结论；
- 候选手段清单：每个手段服务哪个目标、覆盖哪个问题、为什么不选替代方案；
- 关键取舍：所有候选按同一组选型标准比较，说明满足、妥协和淘汰原因；
- 叶子手段契约：责任人、触发条件、输入、动作、输出证据、验收标准、异常处理。

用户如果把手段提前说得很细，Agent 要做两步：

1. 反向追问它满足哪些选型标准和场景约束、来自什么业务特点、服务哪个目标、解决哪个问题，
   以及对比放弃了什么方案。
2. 若回答不出来，手段保留在“候选/待验证”，不得写入 `require_points.md` 的已确认手段。

### Phase 4/4 · CLARIFY

目标是把前面乱序材料投影成一份干净的 `require_points.md`。这一步不是抄聊天记录，而是做
结构化归位和准出检查。

必须完成：

- 本轮所有新增上下文都有吸收、合并、待确认或排除结论，材料账本不存在未处理项；
- 需求背景、问题、目标、业务特点、场景约束、选型标准、方案调研、候选和选定手段均非空；
- 问题恰好三个，目标恰好三个，且一一呼应；
- 方案调研一到三项，且每项都实际影响选型；
- 每项场景约束都有业务特点或目标来源，每项选型标准都能用于比较和淘汰候选；
- 每个选定手段都能经过选型标准和场景约束回扣业务特点、目标和问题，并有叶子契约；
- 全文通过语义归位与推导连续性门禁，没有错位、推导跳跃、业务脱节、悬空内容或过渡缺失；
- `require_points.md` 通过陌生评委理解门禁，评委不借助聊天上下文也能复述项目主线；
- 决策树所有分支已访问，Frontier 为空，不存在被未完成事实检索阻塞的隐藏分支；
- 所有 AI 推导项均标注并获得用户确认；
- Open Questions 为空；
- 用户明确确认已经达成共同理解。

只有本阶段准出通过，才允许写入 `require_points.md` 并交给用户审核。用户说“先写一版”时，
如果仍存在阻塞性缺口，可以写“草案”，但必须在文首列出未确认项，并禁止进入最终 `方案.md`。

## 决策树与 Frontier 追问循环

每轮对话按固定顺序执行：

1. 读取当前 `.promotion/brainstorm.md`、`require_points.md`、`evidence.md` 和已有 `方案.md`。
2. 把用户最新输入拆成背景事实、问题、目标、业务特点、外部支持、场景约束、选型标准、调研、候选手段、效果、规划、待确认。
3. 与当前 Requirement 基线比较，标记新增、补证、细化、修改、删除、冲突或纯表达。
4. 按输入种子方向执行双向切片，再做覆盖决策、重新投影和连续性门禁。
5. 把所有待用户决定的内容更新成带依赖关系的决策树；把可自行查明的内容列为事实任务并立即查找。
6. 重算 Frontier，只纳入前置决策和事实均已解决的节点；被本轮答案依赖的节点延后。
7. 更新 `.promotion/brainstorm.md`，保留用户原话、归位判断、影响范围、覆盖结论、决策树、Frontier 和事实任务。
8. 一次向用户提出整个 Frontier，每题编号并给推荐答案，然后停止推进等待回答。

同一 Frontier 内按风险排序：

1. 会改变需求背景、外部支持前提或个人边界的问题；
2. 会改变三个问题或三个目标的问题；
3. 会改变业务特点、场景约束或选型标准的问题；
4. 会改变选型和主手段的问题；
5. 会影响指标、事实来源或个人贡献归因的问题；
6. 只是措辞、标题或展示顺序的问题。

问题必须使用：

```text
❓ **Q1** - **<问题标题>**: <问题正文和互斥选项>

➡️ <推荐答案及简短理由>
```

Frontier 为空不自动代表澄清完成：仍有事实任务或被阻塞节点时继续查明事实；所有分支都已解决后，
先展示共同理解和 `require_points.md` 预览，等待用户明确确认，不能自动进入方案写作。

## Requirement 文档准则

`require_points.md` 是设计前唯一事实源，模板见
[`references/require-points-template.md`](references/require-points-template.md)。它面向作者和评审者，
不是机器 Trace。正文不展示内部字母编号、节点编号、映射表或聊天流水账；推理关系通过自然语言
写清楚。

固定结构为：项目开场摘要 → 项目边界与评审语境 → 关键上下文 → 需求背景 → 三个问题 → 三个
目标 → 业务特点与场景约束 → 方案调研 → 候选手段与取舍 → 选定手段闭环 → 效果与证据 → 规划
与不做范围 → 上下文覆盖和切片检查 → 陌生评委理解检查 → 用户审核。新增信息只能投影进这套
结构，不能创建平行附录或临时章节逃避归位。

写作要求：

- 全部上下文按语义吸收到稳定结构中，不逐字复制对话，也不把新增信息作为补丁句堆在章节末尾；
- 背景先于问题，问题先于目标；业务特点与目标共同推出场景约束，场景约束先转成选型标准，再进入调研、候选比较和手段；
- 每句话只承担一个主语义角色；同一句同时讲问题和“准备怎么做”时，拆句并分别归位；
- 不把手段包装成问题，例如“缺少平台”不是问题，问题应写成“人工判断分散导致风险不可控”；
- 不把收益包装成目标，例如“提升 30%”必须说明提升什么、来自哪个问题、如何验证；
- 不把调研写成名单，每个调研对象都要给出借鉴点、边界和结论；
- 不把“高性能、高可用、易维护”等通用愿望冒充业务特点；业务特点必须有项目事实和选型影响；
- 不把团队偏好冒充业务特点；可以保留为组织约束，但必须标明来源和权重；
- 不把候选手段直接写成最终方案，必须有取舍和放弃理由；
- 不用“平台化、闭环、治理、智能化”等抽象词替代真实机制。

语义角色、正向连续性、反向可追溯、章节过渡和 Review 输出格式只定义在
[`references/semantic-continuity-gate.md`](references/semantic-continuity-gate.md)。生成或审校任何
Requirement 或方案正文时必须读取并执行；只检查标题、技术词或固定关键词不算完成。

陌生评委的认知假设、冷读步骤、复述测试、时长检查和 Review 输出格式只定义在
[`references/reviewer-comprehension-gate.md`](references/reviewer-comprehension-gate.md)。执行时只能
读取当前审核产物，不能用聊天记忆替文档补背景。

## 正向与反向切片

正向切片用于从背景、问题、目标和业务特点向下推导缺口：还缺哪些场景约束、选型标准、调研、
手段、风险兜底和效果口径。
每轮都执行；若本轮没有新增上游内容，也要记录“无新增正向缺口”。

反向切片用于从新出现的手段、效果、调研或规划向上找归属：它满足哪个选型标准和场景约束、
对应什么业务特点、解决哪个问题、服务哪个目标，是否需要补充上游背景或修改既有选型。每轮都执行；若本轮没有新增下游内容，也要记录“无新增
反向影响”。

反向切片结论有三种：

- 能经过既有选型标准和场景约束回扣业务特点、问题和目标：补入候选手段、选定手段或效果证据；
- 需要新增或修改上游：先问用户是否更新背景、问题、目标、业务特点、场景约束或选型标准，确认前不得改最终 Requirement；
- 无法归属：保留在待确认，不塞进问题章节，也不写进最终方案。

合并规则：

- 正向和反向都指向同一章节：更新该章节草案；
- 正向要求补上游、反向要求挂手段：先补上游，手段保持候选；
- 反向发现新手段推翻既有目标或选型：当前 Requirement 进入待确认，不能落盘；
- 两者冲突：新增一个冲突决策节点，按依赖关系放入当前或下一轮 Frontier，不猜测写入。

## 方案写作

`write_promotion_design` 只能在 Workflow 已记录用户确认 `require_points.md` 后执行，基于已确认 Requirement 和证据材料生成 `方案.md`。正文结构以
[`references/promotion-template.md`](references/promotion-template.md) 为唯一模板：

1. 需求背景；
2. 问题；
3. 目标；
4. 方案调研；
5. 解决方案；
6. 效果；
7. 规划。

生成时必须记录并校验所消费的 Requirement 修订，并保持 `require_points.md` 的背景、问题、目标、业务特点、场景约束、选型标准和选型不变。发现新问题、新目标、
新取舍或证据推翻既有选择时，回到澄清阶段更新 `require_points.md`，不能在 `方案.md` 中
静默补齐。写入前再次执行语义归位与推导连续性门禁；若已确认 Requirement 存在错位、推导
跳跃或悬空内容，回到 CLARIFY 修正并重新取得用户确认，不得把断裂推导原样投影进方案。生成后
立即执行陌生评委理解门禁；未通过时不得上报写作或审校通过 Condition。

## 反馈更新

已有 `方案.md` 时，用户反馈先分类：

- 补充或修改背景、问题、目标、业务特点、外部支持、场景约束、选型标准、调研取舍、选型、手段边界、效果口径、规划、个人贡献边界：一律重新打开需求澄清，把反馈作为变更种子写入材料账本，完成双向切片后生成新的 `require_points.md` 修订；不得先改方案。
- 改表达、标题、顺序、例子、图示、证明材料：可直接改 `方案.md`，但不得改变已确认需求含义。
- 反馈无法唯一命中位置：新增“反馈归属”决策节点并放入可用 Frontier，不猜测改写。

每次更新后输出影响清单：反馈原话、材料覆盖结论、命中的 Requirement 段落、反向复核范围、
正向重算范围、受影响方案段落、保持不变范围、仍待确认项。Requirement 发生语义变化时，旧方案
立即标记为 `stale`；新修订通过双门禁和用户审核后，再更新方案并重新冷读。

## Review 门禁

Review 必须先读取并执行
[`references/semantic-continuity-gate.md`](references/semantic-continuity-gate.md)，逐句扫描语义归位，
再对全文执行正向推导和反向追溯。命中任何错位、推导跳跃、业务脱节、悬空内容或过渡缺失时，先输出阻塞
发现，不能先给“整体结构正确”“方向没问题”之类结论，也不能把它降级成措辞建议。

连续性门禁通过后，必须读取并执行
[`references/reviewer-comprehension-gate.md`](references/reviewer-comprehension-gate.md)：只读取当前
产物，以不知道该业务和项目历史的评委身份完成冷读、复述、首次困惑点和时长检查。不得利用
`.promotion/brainstorm.md`、聊天记录或作者口头补充替文档解释。

双门禁通过后，再逐项检查：

- Requirement 是否按背景、问题、目标、业务特点、场景约束、选型标准、调研、手段归位，没有概念偷换；
- 三个问题是否 MECE，三个目标是否逐一回应问题；
- 业务特点是否真实且项目特有，场景约束是否由特点和目标推出，选型标准是否真正用于候选比较；
- 每个手段是否有来源、取舍、输入输出、风险兜底和验收证据；
- 事实、数字、收益和个人贡献是否可回指证据；
- `方案.md` 七段是否完整，且没有脱离 Requirement 发明新内容；
- 晋升表达是否同时呈现业务价值、技术判断、复杂度、个人贡献和可复用沉淀。

完成标准：Review 报告已覆盖每个句子的主语义角色、每条正向链、每个下游节点的反向归属和陌生
评委复述卡，连续性与理解性发现均为零，且其余检查均给出通过或带原文定位的发现。未通过时，先列阻塞项，再给最小
修改建议。不得用“整体不错”掩盖事实缺口。
